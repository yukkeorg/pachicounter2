# 既定フロントはビルドレスで埋め込み、外部ディレクトリで上書きできる

既定のフロントは Node を使わない素の HTML + CSS + ES module とし、`go:embed` でバイナリに
埋め込む。理由は ADR-0005 と同じで、`go build` 一発で配布物が完成する状態を守るため。
ビルドに Node と Parcel が必要になると、配信機や Raspberry Pi でビルドしたいときに前提が増える。
画面に出る要素は数字が 10 個程度で、先行試作 `pcounter-frontend` の TS/SCSS を捨てても等価な
ものが素の JS/CSS で書ける規模である。

ただし将来 React などを使う余地は残す。担保は 3 点。

1. `--front-dir` で指定した外部ディレクトリを埋め込みより優先する（ビルド成果物の `dist/` を
   そのまま指定できる）
2. SSE と POST の HTTP 契約を仕様として固定し、フロントの実装技術から独立させる
3. 開発サーバ向けに `Access-Control-Allow-Origin` を設定可能にする。React を別ポートで動かすと
   オリジンが異なるため `EventSource` がブロックされるので、ここだけはコア側の対応が必要

機種ごとの見た目は、コアが送る `machine.id` と `state.kind` を `<body>` のデータ属性に反映して
CSS だけで切り替える。JS の役割はデータを属性とテキストに流し込むことに限り、機種が増えても
CSS を 1 ファイル足すだけで済む。テーマを書いていない新機種も、機種語彙のラベルはそのまま
表示されるので壊れない。

旧来の配信経路（GStreamer の `textoverlay`/`rsvgoverlay` に Pango markup を流す形）は捨てる。
機種プラグインが参照していた SVG フレーム（`resource/blueflame_wide.svg` など）は git 履歴にも
ディスクにも存在せず、復元すべき旧来の見た目がそもそも残っていない。必要になれば「SSE を
購読して Pango markup を書き出す小さなフロント」として後から足せる。
