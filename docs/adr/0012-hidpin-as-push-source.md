# hidpin は独立した信号源にし、ポート値を 32 ビットにする

hidpin（RP2040 のボードで作る USB-HID の GPIO デバイス。https://github.com/yukkeorg/hidpin）を
信号源に加える。hidpin はピンの変化をデバイスの中でチャタリング除去し、変化が始まった時刻
（デバイスの時計で µs）をつけて送ってくる。USB-IO 2.0 のように、ホストが読みに行くまで今の値を
持っているだけの製品とは形が違う。

## usbhid のドライバにせず、独立した信号源にする

usbhid のドライバ（`internal/hidgpio`）の契約は、今のポート値を返す `ReadPorts` をポーリングする
ことである。hidpin をここに押し込むと、デバイスが打った時刻も、まとめて届く変化の並びも捨てて、
5ms ごとに今の値を読み直すことになる。ADR-0005 がイベントストリーム型を選んだ理由の 1 つが
「マイコン側でエッジを検出して push する形」だったので、hidpin は `-source hidpin` という独立した
信号源にする。

## デバイスの面倒は hidpin の Go ライブラリに任せる

デバイスとのやり取りは hidpin リポジトリの Go ライブラリ（`github.com/yukkeorg/hidpin/host-go`）
を使う。プロトコルの仕様と実装は hidpin 側にあり、ここで書き直すと同じ仕様の実装が 2 つに分かれる。
ライブラリは pure Go で依存が無いので、単一静的バイナリ（ADR-0005）は崩れない。ただし
Linux（hidraw）にしか対応していないので、ほかの OS では起動の時点でエラーにする。

使うのはライブラリの `Watcher` である。これは長く動かすプログラム向けの層で、次を受け持つ。

- デバイスが挿さるまで待ち、抜けたら再接続する
- デバイスの時計をホストの時計に直す（受信の遅れが最も小さい標本を使い、時計どうしのずれに追う）
- 状態通知の読み落とし（`seq` の飛び）を数える
- 待ち行列に残った変化と、Get_Report(Input) で読んだ今の値の食い違いを解く
- 変化の知らせが無いまま値が変わっていたら、それを「推測した変化」として知らせる
- 別のプログラムがピン設定を変えたら追従する

これらは一度この信号源の中に書いたが、ライブラリが同じものを持つと分かった時点で捨てた。
プロトコルの細かい約束事（待ち行列、`OVERFLOW`、`seq`、ピン設定を変えた直後の状態通知）を
2 か所で解釈すると、片方だけが直る事故が起きる。

信号源に残る仕事は、その知らせを生のポート値のイベントに直すことだけになった。

## 極性の解釈はコアだけが持つ

`Watcher` はピンの ON/OFF も教えてくれるが、どのピンがアクティブローかを渡さず、「どのピンも
アクティブハイ」と伝える。こうすると ON/OFF がピンレベルそのものになり、生信号ログにはデバイスの
値がそのまま残る（ADR-0006）。アクティブローの解釈は `-active-low` を持つコアだけが行う。
2 か所で極性を反転させると、ログを再集計したときに符号が合わなくなる。

## ポート値を 32 ビットにし、ビット n を GPIO n にする

`signal.Ports` は 16 ビットだったが、hidpin の GPIO は 0〜29 番まである。監視しているピンを
16 ビットに詰め直す案は、`-wire` に書く番号とボードの印字（GPIO 番号）が食い違い、ピン設定が
変わるたびに番号がずれるので採らなかった。32 ビットにしてビット n を GPIO n とし、`-wire` には
0〜31 を書けるようにする。生信号ログのポート値は JSON の数値なので、これまでの記録はそのまま読める。

監視していないピンのビットは 0 になる。アクティブローの配線では「信号が出ている」ように見え続け、
回転も大当りも数えられないまま静かに壊れる。そこで接続時に、監視しているピンをログに出し、配線した
ビットが監視外の GPIO を指していれば警告する。既定の配線（ビット 0〜3）は Raspberry Pi Pico なら
使えるが、Adafruit QT Py RP2040 には GPIO0〜2 が無いので `-wire` の指定がいる。

この確認のために、指定された配線を `source.Env` で信号源へ渡す。配線は信号源を開く前に読み、記録を
流す信号源では、記録された配線に入れ替わったあとで読み直す。

## 取りこぼしは基準を取り直し、切断と同じに扱う

状態通知の読み落とし、デバイスが変化を捨てたこと、ピン設定の変更は、どれも「今のポート値は
分かるが、そこへ至る変化は分からない」状態である。取りこぼした変化は数え直せないので、
今の値で基準イベントを流し直す。コアはこれを再接続と同じに扱い、生信号ログに `disconnect` を残す。
USB が繋がったままでも `disconnect` と記録されるが、「この間の変化を取り逃した」という意味は
同じなので、新しいレコードの種類は作らない。

基準イベントは、1 つの状態通知から出る知らせが途切れてから 1 つだけ流す。知らせごとに流すと、
1 つの状態通知から基準イベントがいくつも出て、そのたびに `disconnect` が残る。

## 無通信は自分で見張る

`Watcher` は読み取りのエラーで切断に気づくが、USB が繋がったままデバイスが黙る場合は気づけない。
hidpin は変化が無くても 1 秒ごとに状態通知を送るので、その 3 回分が届かなければ監視をやり直す。

## ピン設定は書かない

hidpin の既定のピン設定（使えるピンをすべてプルアップ入力で監視し、チャタリング除去は 20ms）の
まま使い、コアからは書き換えない（`Watcher` の目標ピン設定を渡さない）。どのビットを何に使うかは
今までどおり `-wire` で決まり、デバイスの設定は hidpin の道具で管理する。2 か所から設定を書くと、
互いの変更を打ち消し合う。

チャタリング除去はデバイス（20ms）とコア（8ms）の 2 段になるが、実機のスタート信号のパルス幅は
約 500ms（セッション 20260913-140402 で最短 494ms）なので、デバイスの 20ms で信号が消えることは
ない。
