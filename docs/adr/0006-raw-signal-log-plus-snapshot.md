# 生信号ログと集計スナップショットの二重で永続化する

旧実装は終了時に 1 回だけ集計結果を保存していた（`app.py:102-108`）ため、電源断やクラッシュで
その日の数字が全部消えた。加えて機種ごとに 1 ファイルへ永久に累積し、`-r` を付けるまで昨日の
数字と混ざり続けていた。そこでセッションを集計単位として導入し（CONTEXT.md 参照）、永続化を
二重にする。

- **集計スナップショット**: 値が変わるたびに一時ファイルへ書いて rename する。外部から今の
  状態を 1 ファイルで読めるようにするためと、どのセッションを集計中かを指すため。
- **生信号ログ**: 1 行 1 イベントの JSONL（単調増加時刻・実時刻・変化後のポート値）を追記する。

二重にする理由は、スナップショットだけでは**集計規則を直したときに過去を再集計できない**こと。
実際にこの設計作業で初当たり確率の分母規則を整理し直しており（ADR-0004）、規則の修正は今後も
起きる。生信号が残っていれば、直した規則を過去のセッションにも適用できる。副産物として、
この JSONL はそのまま実機なしのテスト再生素材になる（旧実装にテストが無かったのは、実機と台の
挙動なしには検証できなかったためと見られる）。再生は専用コマンドではなく信号源の 1 実装として
持つので（ADR-0005）、コア本体を `--source file:session.jsonl` で起動すれば集計・スナップ
ショット・SSE・フロントまで通しで検証できる。

**セッションの途中でコアを再起動したときの復帰は、スナップショットではなくログの再集計で行う。**
当初はスナップショットを読むだけで済ませる想定だったが、実装してみると足りないことが分かった。
機種プラグインの内部状態（状態機械や区間ごとの回転数）はスナップショットに現れないため、
ログを流し直さないと復元できない。ログが唯一の真実である以上、復帰もログから行うのが筋である。
数千行を流し直す処理は一瞬で終わるので、速さの面でも困らない。

SQLite は採らない。`mattn/go-sqlite3` は cgo を要求して ADR-0005 と衝突し、pure Go の
`modernc.org/sqlite` はこの用途（追記と全読み）には重い。

保存先は `$XDG_STATE_HOME/pachicounter/`（既定 `~/.local/state/pachicounter/`）、Windows は
`%LocalAppData%\pachicounter\`。旧実装の `~/.config/pcounter.d/` は設定用ディレクトリに状態を
置いていた。

セッションの区切りは明示操作（`POST /session/new`）で行い、起動時は直近のセッションを継続する。
配信中にデバイスを抜き差ししてコアだけ再起動したいときに、セッションが意図せず切れないため。

**記録を再生して起動したとき（`--source file:` / `loop:`）は、保存先に何も書かない。** 続きの
セッションにもつながず、生信号ログもスナップショットも書かない。数字は HTTP と SSE で見るだけに
なる。当初は再生も実機と同じ保存先を使っていたため、直近のセッションと機種が同じだと「続き」と
みなされ、実機のセッションのログに再生した信号が追記されていた。唯一の真実であるログに写しが
混ざるのは、この ADR が避けたかったことそのものである。再生元のファイルがすでに記録そのもの
なので、写しを作る理由も無い。同じ理由で、再生中は補正と新しいセッションの操作を受け付けない
（補正はログに残すものである。ADR-0008 を参照）。
